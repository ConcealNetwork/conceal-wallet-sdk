Deposit interest parity

Operator brief — what we will build

TL;DR

Withdrawals built by the web wallet can fail on-chain when JavaScript interest is off by one atomic unit from the Conceal daemon. We will make the SDK’s interest math match the daemon operation-for-operation, and pin that with golden tests.

What you'll get

  • Interest amounts that the node accepts (same as Currency.cpp for V1/V2/V3).
  • A documented parity table explaining each version’s math.
  • CI that fails if JS ever drifts from daemon-verified fixtures.
  • Updated next-wallet golden tests so they stop pinning old float artifacts.

How it works

The daemon uses 32-bit floats (and a special pow step for long investments). The wallet today uses 64-bit floats, which sometimes floors one unit low (famous case: exact 540,000,000 becomes 539,999,999). We mirror the daemon’s float steps in JS, and for the pow step we ship a tiny precomputed table generated from C++ so browsers never depend on their math library. 

flowchart LR
  A[Deposit amount + term] --> B{Version?}
  B -->|V1| C[BigInt divide - unchanged]
  B -->|V3 / V2 weekly| D[float32 op mirror]
  B -->|V2 investment| E[lookup m8 table]
  E --> D
  D --> F[trunc to atomic interest]
  C --> F
  F --> G[Scan stores interest]
  F --> H[Withdraw recomputes same function]
  H --> I[Redeem output amount]

What changes for you

  • No new CLI or UI — same SDK APIs.
  • Some displayed/stored interest numbers for old V2/V3 deposits may change by a few atomic units to match the chain (correct behavior).
  • If a wallet still has a wrong stored interest, withdraw will refuse until a resync recomputes it (safer than signing a bad tx).

Risks and open questions

  • Investment table must be regenerated if consensus ever changes the investment formula.
  • Live daemon RPC fallback for exotic terms is deferred; unsupported table keys throw.

Out of scope

  • Changing the C++ daemon.
  • WASM rewrite of Currency.
  • Pull request / publish unless you ask.
